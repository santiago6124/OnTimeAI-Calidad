# Matriz ISO/IEC 25010 de OnTimeAI

Mismo formato que el ejercicio de Knight Capital de la cátedra: para cada
característica, si está comprometida hoy, la evidencia concreta del proyecto y
la práctica que la sostiene o la corrige. Evidencia tomada de los repos, de
`AGENTS.md` del workspace y de las mediciones de `mediciones/`.

## Top 3, de mayor a menor impacto

1. **Fiabilidad.** Es la única característica que ya produjo incidentes con
   pérdida de servicio: una base corrupta y un proyecto entero inoperable. Un
   sistema que predice demoras y no está disponible a la hora de la salida no
   sirve, por buena que sea la predicción. Por eso las pruebas de integración
   real y el smoke post-deploy apuntan a la base compartida y al servicio vivo.
2. **Adecuación funcional.** El producto es la predicción; una calibración rota
   convierte una buena discriminación en una alerta que marca el doble de
   vuelos de lo que debería, y el usuario deja de confiar. Es además el eje de
   la tesis, así que se mide en continuo.
3. **Mantenibilidad.** No afecta al usuario hoy, pero es lo que decide si las
   dos anteriores se sostienen: el archivo con más fixes es el más grande y la
   función más compleja es la menos cubierta. El gate de complejidad y los
   trinquetes de cobertura son la práctica que corta ese círculo.

Eficiencia de desempeño queda cuarta: importa porque el ciclo condiciona el
horizonte de predicción, pero hasta este TP no había mediciones de la API bajo
carga, y los umbrales recién se fijan con k6.
